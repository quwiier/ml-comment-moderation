## BPMN AS-IS: спецификация

**Пулы:** «Пользователь» и «Социальная сеть / модерация». Во втором пуле дорожки «Платформа» и «Модератор».

**Happy path:** message start «Комментарий опубликован» → user task «Пользователь видит комментарий» → XOR «Поступила жалоба?» → при `нет` end «Остаётся опубликован»; при `да` manual task «Прочитать комментарий и контекст» → XOR «Нарушение?» → user task «Оставить / скрыть / удалить» → end «Решение применено».

**Апелляция:** message catch «Апелляция» → manual task «Повторно проверить» → XOR «Отменить решение?» → service task «Восстановить контент» либо «Оставить решение» → end.

**Объекты данных:** комментарий, жалоба, правила, решение. В AS-IS отсутствуют inference, confidence routing и системный feedback dataset. Ошибка платформы представлена boundary error у регистрации жалобы с ручной регистрацией/повтором.

## BPMN TO-BE: спецификация

**Пулы:** «Пользователь» и «ML-платформа модерации». Дорожки: «Социальная сеть», «ML-контур», «Модератор», «Данные и ML Ops».

**Основной поток:** message start → service tasks «Сохранить и опубликовать», «Записать событие», «Предобработать», «Получить prediction», «Применить policy» → XOR «Маршрут риска».

- `ALLOW`: оставить видимым → записать автоматическое решение и служебное feedback-событие; случайная выборка дополнительно поступает в ручной аудит по правилу Policy Engine.
- `REVIEW`: создать обычную задачу → user task модератора → применить финальное решение.
- `TEMP_HIDE`: временно скрыть → создать приоритетную задачу → user task модератора → применить финальное решение.

Boundary error/timeout на inference ведёт к service task «Fallback: правила» и затем к ручной очереди. Низкая уверенность — условие ветки `REVIEW`. После решения parallel gateway отправляет audit event и feedback event. Message catch апелляции ведёт к повторной проверке и при отмене — восстановлению. Feedback pipeline формирует dataset version; задача обучения включает quality/bias/security gates и ручное одобрение до регистрации версии модели.

Файлы SVG намеренно являются компактными презентационными схемами и не заменяют формальные исходники `.bpmn`: все события, условия, message flows и BPMN DI зафиксированы именно в XML-моделях.

**Объекты данных:** CommentEvent, Prediction, PolicyVersion, ModerationDecision, Appeal, FeedbackEvent, DatasetVersion, ModelVersion, AuditEvent.

## Отличия и эффект

| Изменение | Ожидаемый эффект-гипотеза |
|---|---|
| Event bus | Нет потери при кратком сбое, сглаживание пика |
| ML + policy | Быстрая оценка всего потока, единая версия правил |
| Три маршрута | Ресурс человека направлен на риск, FP остаётся контролируемым |
| Временное скрытие + апелляция | Обратимость высокорискового авто-действия |
| Audit + feedback | Воспроизводимость и улучшение на подтверждённых данных |

## Проверки BPMN

- XML использует BPMN 2.0 namespaces и BPMN DI.
- Sequence flow не пересекает границы pools; между pools используются message flows.
- XOR имеют именованные условия/default; parallel gateway не используется как XOR.
- Error/timeout, low-confidence, escalation, appeal и feedback представлены явно.
- Импорт и визуальную читаемость следует подтвердить в bpmn.io/Camunda Modeler перед сдачей.
